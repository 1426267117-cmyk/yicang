建议在 ERP 内保存以下独立层次；字段名是设计建议，不是当前看板已存在的接口承诺。

原始读取层：platform、store_id、source_order_id、source_updated_at、fetched_at、原始响应、响应签名/哈希、接口版本、同步批次。个人信息按实际权限和 ERP 访问控制保存，不写普通日志。
订单主表：源订单号、创建/更新时间、源时区、currency、付款状态、取消状态、履约状态、商品额、折扣、运费、税费、已付款/已退金额及金额口径。
订单行：源订单行ID、原始SKU、平台商品/变体ID、标准SKU映射及状态、订购/取消/退款/发货数量、原始单价、行级折扣/税/金额。
退款与交易：退款对象ID、支付交易ID、交易类型/状态、币种/金额、发生/结算时间、关联订单/订单行。失败交易不能算已退款，对象和交易不能双计。
履约与包裹：源履约ID、订单行及数量、仓库、发货单、承运商、轨迹号、状态、原始预计/实际日期；允许一单多包裹、多仓、部分发货。
仓储与入库：仓库代码、原始SKU、批次、可用/锁定/在途、来源更新时间、入库计划号、运单号、柜号或明确柜数。发货单数、柜数、商品件数和SKU种类数分别保存。
同步状态：平台/店铺/资源的游标、更新时间水位、去重键、失败与重试、最后成功时间及覆盖范围。游标和业务事实成功提交应保持一致，失败不能跳过未落库页。

主键：订单 platform+store_id+source_order_id；订单行再加 source_order_line_id。不同平台/店铺同一字符串订单号不能合并。
新增/变更：按上游更新时间增量，保留分页游标与可配置重叠重扫。Webhook 只在获准后配置，并验签、去重、持久化处理状态，定期用 API 对账补漏。
日期：源原始时间不覆盖；另行计算店铺日、洛杉矶业务日及北京时间快照日。广告账户日历日期与店铺业务日期不能直接视为一致。
金额：decimal 或最小货币单位，保留币种，不用浮点累计。原始订单事实保留税、运费和折扣，报表层再按口径计算。ShopifyQL 财务口径与订单流水可能不同，需差异桥接，不能为凑数篡改单价。
业务归属：ERP 收全店原始订单。看板 SZ-/ZC-SZ-/ZC1-SZ-/ZC2-SZ-/LH-SZ- 等归属排除只影响报表，不应删除 ERP 原始订单或订单行。
未知：无权限、无来源、字段缺失、暂未结算都保持未知；有明确来源零值才是0。匹配不到SKU不等于零销量；没有成交价不等于零货值。

第一阶段只读验收：
1. 一家 Shopify 店完整分页回补一个明确区间，记录订单数、订单行数和 API 覆盖范围；别只拿第一页。
2. 同批数据重复执行两次，业务记录不增加；更新已有订单时不生成重复订单。
3. 验证 Pending、零金额、测试、取消、部分退款、后续发货、拆单/多包裹都能按状态保留。
4. 断网、限流、超时、鉴权失效后保留已成功事实；重跑接续游标，不清空原表，不默默写0。
5. 按平台官方字段解释订单/退款/支付金额，再与看板相同日期/币种/归属范围对账；列明税费、订单状态和结算日期差异。
6. 在 ERP 确认正式订单 API 权限后才进行真实单店试采。地址/买家等受保护字段按实际获批范围保存，未获批时明确缺项。
7. 看板线上、采集任务、共享盘原始文件、已有平台授权均保持原样。
